## P0 — prerequisite for any real-hardware pilot

1. **~~Extension-flood / horizon gating / reservation enforcement.~~ FIXED** (commits `9f5d78f`, `30355ee`, `a808916`, `290d976`, `085288d`). `Orchestrator.runRouting()` (packages/orchestrator/src/orchestrator.ts:642-692) used to append one node + re-send a stitching order EVERY tick regardless of robot catch-up. Consequences (measured in sim soak): throughput collapse ~20s/cell on legs >5 cells; sustained same-cell overlaps under wall-clock (45 in one run); occasional permanent reservation deadlock (foreign-owned current cell → empty grant forever). Reservation claims were advisory (didn't block sendMission) — contradicted spec's "router optimism never bypasses reservations". Fixed via horizon-gated frontier extension (only extends when the robot is within `opts.horizon` nodes of its commanded frontier), reservation claims now block extension (full-grant-or-nothing), a deadlock backstop force-requeues genuinely stuck robots (`opts.blockedTicksLimit` consecutive blocked ticks), and a frontier-race resume path (using both `rt.currentNodeId` and `rt.lastVdaNodeId` as signals) so a robot that's genuinely on its committed path resumes instead of being wrongly requeued. The regression gate at packages/sim/test/e2e.test.ts (`expect(collisions.sustained).toEqual([])`) is restored and green: 0 sustained/soft collisions across repeated runs. The 10-robot/20-order soak sits at exactly the 95% completion gate (19/20) — the one non-completing order in every observed run is the parked-idle-robot limitation, see new P2 item below, not a recurrence of the extension flood. A new 1-robot/9-cell latency test (packages/sim/test/e2e.test.ts) proves the fix directly: ~9.0-9.1s wall for a leg that took >180s (~20s/cell) pre-fix.
14. **~~No reconciliation/alarm when a legged robot's reported node falls off its committed window.~~ FIXED** (commits `cb425db`, `08bdff2`, `c9f4dce`). Nothing in `Orchestrator` used to detect or alarm when a legged robot's `currentNodeId` resolved to a node that wasn't part of its own `leg.nodeIds` window (real-world avoidance swerves, manual/teleop moves, or a bumped AGV) — the pipeline just kept trusting the last-known committed path as if nothing happened. Fixed via an off-window reconciliation check in `runRouting()`'s progress scan: two consecutive ticks where `currentNodeId`/`lastVdaNodeId` are found nowhere in `leg.nodeIds` (transient-snap-tolerant via `leg.offWindowTicks`) triggers `recoverLeg()` — alarm, cancel, requeue order (or clear a yield leg), `releaseAll` + own-cell re-claim. Covered by unit tests in orchestrator.test.ts ("off-window reconciliation (#14)").
15. **~~No physical-progress watchdog for a robot stalled on a fully-extended path.~~ FIXED** (commits `cb425db`, `08bdff2`, `c9f4dce`). A robot that stopped moving while genuinely `EXECUTING` a mission whose frontier already equalled the leg goal (nothing left to extend) had no backstop: `runRouting()`'s horizon/contention-blocked branches never ran (no pending extension to block), so a stuck-but-still-connected robot just silently sat there holding its order forever, with no timeout until the connection itself eventually dropped. Fixed via `RobotLeg.lastProgressTick` (set at leg creation, updated on every `progressIndex` advance and on frontier-race resume) and a watchdog check in `runRouting()`: `tickCount - leg.lastProgressTick >= opts.watchdogTicks` (default 40, intentionally above `blockedTicksLimit`'s 20 so the contention backstop wins where both apply) triggers the same recovery path as #14. Covered by unit tests in orchestrator.test.ts ("physical-progress watchdog (#15)").

13. **~~Parked idle robot on the only path drives orders into backstop-requeue.~~ FIXED** (commits `434722d`, `8c51327`). A parked IDLE robot sitting on the only path into an order's pickup/drop permanently owned that cell but was never itself commanded to move out of the way — PIBT only ever pushed it virtually (treated it as an obstacle for planning), never dispatched an actual parking/yield move. Such an order blocked every extension attempt until the deadlock backstop (`opts.blockedTicksLimit` consecutive fully-blocked ticks, default 20) requeued it; after 3 requeues `OrderBook` failed it outright rather than ever routing around the parked robot. This was the exact cause of the 10-robot/20-order soak's one non-completing order (19/20 = 95.0%, sitting exactly at the regression gate). Fixed via yield-leg dispatch: `RobotLeg` gained `kind: "order" | "yield"`; when a blocked ORDER leg's `blockedTicks` reaches `opts.yieldAfterTicks` (default 6), a qualifying blocker (online, un-quarantined, leg-less robot owning the contested cell) is BFS-routed (depth cap 10) to a free, unoccupied node and dispatched a `kind:"yield"` leg via the same reservation-gated leg machinery as order legs (no collision-invariant change); yield completion is handled explicitly in `handleMissionDone`/`handleMissionFailed` by missionId shape (`yield:` prefix), before order-book logic, and never touches the order book. Anti-thrash via `rt.lastYieldTick`/`opts.yieldCooldownTicks` (default 20). Covered by unit tests in orchestrator.test.ts ("yield dispatch (#13)").

## P2 — pre-pilot findings (final whole-branch review, 2026-08-11, round 3)

16. **Off-window recovery (#14) can leave a drifted robot cell-less inside another robot's already-granted committed window.** `recoverLeg()`'s own-cell re-claim (`executeRecovery()`) claims whatever `rt.currentNodeId` resolves to at recovery time — if the drift genuinely carried the robot onto a cell another robot's leg has ALREADY validly claimed as part of its own committed extension window (not a collision-hole bug, just two robots' true positions and reservation state disagreeing after an off-path event), the re-claim legitimately returns an empty grant (claim() is a no-op when the first cell is foreign-owned) and the drifted robot is left owning NOTHING — the existing "idle self-claim of X DENIED... collision-hole invariant violated" alarm fires, but nothing auto-halts the fleet. Runbook implication until an auto-halt mechanism exists: pilot operators must treat that exact alarm string as a hard STOP-and-inspect signal, not a log line to shrug off — a robot with no cell ownership at all is a genuine physical-safety gap (nothing prevents another robot's committed path from being granted through wherever it's actually standing). Add to the pre-hardware-pilot runbook explicitly; revisit once an automatic fleet-pause-on-invariant-violation exists.
17. **Same-tick duplicate yield-target selection across two independently blocked robots.** `tryDispatchYield()` is called once per blocked robot per tick it crosses `yieldAfterTicks`; if TWO different robots become blocked by the SAME parked robot (or by two different parked robots that both BFS to the same nearest free cell) in the same tick, both calls run against the reservation table as it stood at the START of this tick's `runRouting()` pass — `findYieldTarget()` doesn't see the OTHER call's just-assigned target (leg assignment happens synchronously inside the loop, but the second call's BFS re-derives "unowned" freshly each time, so it CAN legitimately pick the same free cell the first call just picked before that first blocker has had any tick to actually claim/occupy it via reservation). This is safe — not a collision risk — because actual movement is still gated by the ordinary reservation-claimed extension in `runRouting()`: whichever of the two yielded robots reaches the reservation `claim()` for that shared cell first (via normal PIBT/priority resolution) wins it; the other's yield leg simply blocks (counted as an ordinary blocked yield leg, eventually recovered by the deadlock backstop if it can't find another route) exactly like any other contested-cell scenario. Net effect observed: a brief bit of thrash (one extra blocked-then-abandoned yield leg) in a rare double-blocker coincidence, never a safety issue. Left as-is; revisit only if soak telemetry ever shows this thrashing measurably hurting throughput.
18. **Soak alarm-cap (#8, `pushAlarm()`'s 500-entry ring buffer) could someday false-fail the failure-injection test's `sawOfflineRequeue` check if a run's alarm count exceeds the cap.** That check scans `getAlarms()` for a specific substring; if the cap has evicted the alarm that would have matched (because 500+ OTHER alarms accumulated first), the assertion would wrongly read "never happened" when it did. Not observed in practice — the largest alarm count seen across repeated soak+failure-injection runs to date is 362 (see item 13's soak-gate note above), comfortably under the 500 cap — but there's no structural guarantee against a future, noisier scenario (more robots, longer runs, tighter contention) pushing a run's alarm count past 500 before the specific event the test is checking for occurs. If this test ever starts flaking, check the alarm count/histogram before assuming a real regression — it may just be the cap silently evicting the evidence.

## P2 — Plan 2 findings (api + dashboard, Task 14 final review, 2026-08-11)

13. **`aedes`'s ESM default-import breaks bare-`node` runs of `robot-interface` consumers.** `@tez/robot-interface`'s barrel (`index.ts`) unconditionally re-exports `startDevBroker` (`dev-broker.ts`), which does `import { createBroker } from "aedes"` at module top level. `aedes` exports via a chained `module.exports = Aedes.createBroker = Aedes` assignment that Node's native ESM loader (`cjs-module-lexer`) doesn't recognize as a named export, so `import { createBroker } from "aedes"` throws `SyntaxError: The requested module 'aedes' does not provide an export named 'createBroker'` under plain `node` — reproduces even outside tsx/bundlers. `scripts/demo.mjs` works around this with a `--import` module hook (`aedesShimImportUrl()`) rewriting the import at load time; every other bare-`node` consumer of `@tez/robot-interface` hits the same wall. Fix belongs in `@tez/robot-interface` (out of Plan 2's edit scope): either lazy-`import()` `startDevBroker`'s aedes dependency, or import aedes via its default export and destructure `createBroker` from that.
14. **`demo:vda` AGV-id mismatch + missing `BROKER_URL` log line.** `packages/sim`'s `spawnFleet` mints ids as `sim-001..sim-00N`, but the demo/api side's `FakeAdapter` fleet (used by plain `pnpm demo`) uses `r1..r3` — the two naming schemes don't line up, so a `pnpm demo:vda` run can show a dashboard fleet rail seeded from one scheme against orders/robots referencing the other, confusing the live view. Separately, `packages/api/src/main.ts` never logs a `BROKER_URL=<url>` line, so `scripts/demo.mjs`'s `--vda` path can't discover the dev broker's actual URL from api stdout and falls back (after a 5s grace wait) to the dev broker's hardcoded default `mqtt://localhost:1883`. Fix: unify the id scheme (or make the api's demo seed order/robot fixtures aware of both), and add the missing log line to `main.ts`.
15. **Root `vitest.workspace.ts` runs `packages/*/test` in `environment: "node"`.** The dashboard's `.test.tsx` files need `jsdom`/`happy-dom` for DOM APIs; under the root `pnpm -r test` invocation each package's own `vitest.config.ts` (with its own `environment` setting) is not what runs — the root workspace config's single global `node` environment applies instead, and dashboard DOM-dependent tests fail there. Per-package `pnpm --filter @tez/dashboard test` is unaffected (uses that package's own vitest config) and is green. Fix: give the workspace config a per-package environment override (e.g. `environment: "happy-dom"` scoped to `packages/dashboard/test/**`) or drop the root workspace file in favor of always running tests per-package.
16. **Alarm strings are raw, untranslated English orchestrator log lines.** `StateFrame.alarms` (`packages/api/src/ws.ts`) forwards the orchestrator's alarm strings verbatim; `AlarmDrawer` (`packages/dashboard/src/components/AlarmDrawer.tsx`) renders `alarms: string[]` directly with no lookup through `i18n.ts`'s `STRINGS`/`t()`. Under RU/UZ UI, alarm text still reads in English. Fix needs either a structured alarm shape (code + params) from the orchestrator that the dashboard can map through `t()`, or a client-side regex/keyword translation table as a stopgap.
17. **Orchestrator lacks a public `cancelOrder` API.** `DELETE /orders/:id` (`packages/api/src/routes/orders.ts`) returns `501 {"error": "cancel not supported: orchestrator exposes no cancel API (see docs/PLAN2-HOOK-REQUESTS.md)"}` because `OrderBook` (which does support a `canceled` transition from any non-terminal state) is a private field of `Orchestrator` with no exposed cancel method. Full request/rationale/proposed signature in `docs/PLAN2-HOOK-REQUESTS.md`.

## P2 — Plan 2 findings (final whole-branch review, Task 15/16, 2026-08-11)

18. **WS frame payload grows monotonically.** `makeFrame` (`packages/api/src/ws.ts`) calls `system.orchestrator.snapshot()` and serializes `.orders` — the orchestrator's *full* `allOrders` list, terminal statuses included — into every 10Hz broadcast frame. Nothing ever prunes completed/failed/canceled orders out of that list, so a long-running recording session (the President Tech Award video is exactly this) makes each WS frame larger over time, and every connected dashboard re-parses the growing JSON 10x/second. Orchestrator-side fix (out of Plan 2's edit scope — `orchestrator.ts` is fix-session-owned): either the orchestrator caps/rolls off terminal orders from `snapshot().orders`, or `makeFrame` gets a hook to request only non-terminal + recently-terminal orders.
19. **No production serving story for the dashboard.** The only way to run `@tez/dashboard` today is `vite dev` (see `packages/dashboard`'s `pnpm dev`) with its dev-server proxy to `@tez/api`; `packages/api` never serves a built `dist/` (no static-file plugin registered, no `vite build` step wired into `api`'s startup). Fine for the filmed demo (`pnpm demo` boots both dev servers), but this needs a real answer — `@fastify/static` serving `packages/dashboard/dist` behind the same origin as the API, or a separate reverse proxy — before any real-hardware pilot deploys the dashboard anywhere but a developer's laptop.
