## P0 — prerequisite for any real-hardware pilot

1. **~~Extension-flood / horizon gating / reservation enforcement.~~ FIXED** (commits `9f5d78f`, `30355ee`, `a808916`, `290d976`, `085288d`). `Orchestrator.runRouting()` (packages/orchestrator/src/orchestrator.ts:642-692) used to append one node + re-send a stitching order EVERY tick regardless of robot catch-up. Consequences (measured in sim soak): throughput collapse ~20s/cell on legs >5 cells; sustained same-cell overlaps under wall-clock (45 in one run); occasional permanent reservation deadlock (foreign-owned current cell → empty grant forever). Reservation claims were advisory (didn't block sendMission) — contradicted spec's "router optimism never bypasses reservations". Fixed via horizon-gated frontier extension (only extends when the robot is within `opts.horizon` nodes of its commanded frontier), reservation claims now block extension (full-grant-or-nothing), a deadlock backstop force-requeues genuinely stuck robots (`opts.blockedTicksLimit` consecutive blocked ticks), and a frontier-race resume path (using both `rt.currentNodeId` and `rt.lastVdaNodeId` as signals) so a robot that's genuinely on its committed path resumes instead of being wrongly requeued. The regression gate at packages/sim/test/e2e.test.ts (`expect(collisions.sustained).toEqual([])`) is restored and green: 0 sustained/soft collisions across repeated runs. The 10-robot/20-order soak sits at exactly the 95% completion gate (19/20) — the one non-completing order in every observed run is the parked-idle-robot limitation, see new P2 item below, not a recurrence of the extension flood. A new 1-robot/9-cell latency test (packages/sim/test/e2e.test.ts) proves the fix directly: ~9.0-9.1s wall for a leg that took >180s (~20s/cell) pre-fix.
14. **~~No reconciliation/alarm when a legged robot's reported node falls off its committed window.~~ FIXED** (commits `cb425db`, `08bdff2`, `c9f4dce`). Nothing in `Orchestrator` used to detect or alarm when a legged robot's `currentNodeId` resolved to a node that wasn't part of its own `leg.nodeIds` window (real-world avoidance swerves, manual/teleop moves, or a bumped AGV) — the pipeline just kept trusting the last-known committed path as if nothing happened. Fixed via an off-window reconciliation check in `runRouting()`'s progress scan: two consecutive ticks where `currentNodeId`/`lastVdaNodeId` are found nowhere in `leg.nodeIds` (transient-snap-tolerant via `leg.offWindowTicks`) triggers `recoverLeg()` — alarm, cancel, requeue order (or clear a yield leg), `releaseAll` + own-cell re-claim. Covered by unit tests in orchestrator.test.ts ("off-window reconciliation (#14)").
15. **~~No physical-progress watchdog for a robot stalled on a fully-extended path.~~ FIXED** (commits `cb425db`, `08bdff2`, `c9f4dce`). A robot that stopped moving while genuinely `EXECUTING` a mission whose frontier already equalled the leg goal (nothing left to extend) had no backstop: `runRouting()`'s horizon/contention-blocked branches never ran (no pending extension to block), so a stuck-but-still-connected robot just silently sat there holding its order forever, with no timeout until the connection itself eventually dropped. Fixed via `RobotLeg.lastProgressTick` (set at leg creation, updated on every `progressIndex` advance and on frontier-race resume) and a watchdog check in `runRouting()`: `tickCount - leg.lastProgressTick >= opts.watchdogTicks` (default 40, intentionally above `blockedTicksLimit`'s 20 so the contention backstop wins where both apply) triggers the same recovery path as #14. Covered by unit tests in orchestrator.test.ts ("physical-progress watchdog (#15)").

13. **~~Parked idle robot on the only path drives orders into backstop-requeue.~~ FIXED** (commits `434722d`, `8c51327`). A parked IDLE robot sitting on the only path into an order's pickup/drop permanently owned that cell but was never itself commanded to move out of the way — PIBT only ever pushed it virtually (treated it as an obstacle for planning), never dispatched an actual parking/yield move. Such an order blocked every extension attempt until the deadlock backstop (`opts.blockedTicksLimit` consecutive fully-blocked ticks, default 20) requeued it; after 3 requeues `OrderBook` failed it outright rather than ever routing around the parked robot. This was the exact cause of the 10-robot/20-order soak's one non-completing order (19/20 = 95.0%, sitting exactly at the regression gate). Fixed via yield-leg dispatch: `RobotLeg` gained `kind: "order" | "yield"`; when a blocked ORDER leg's `blockedTicks` reaches `opts.yieldAfterTicks` (default 6), a qualifying blocker (online, un-quarantined, leg-less robot owning the contested cell) is BFS-routed (depth cap 10) to a free, unoccupied node and dispatched a `kind:"yield"` leg via the same reservation-gated leg machinery as order legs (no collision-invariant change); yield completion is handled explicitly in `handleMissionDone`/`handleMissionFailed` by missionId shape (`yield:` prefix), before order-book logic, and never touches the order book. Anti-thrash via `rt.lastYieldTick`/`opts.yieldCooldownTicks` (default 20). Covered by unit tests in orchestrator.test.ts ("yield dispatch (#13)").
