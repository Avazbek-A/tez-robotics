URL: github.com/opentcs/opentcs. ### 1.1. Архитектурная сердцевина: зарядка = обычный заказ + флаг dispensable

Зарядка и парковка **не** отдельная подсистема — это `TransportOrder` типов `CHARGE`/`PARK`, созданные диспетчером самому себе. Вся конкуренция с реальными заказами решается тремя механизмами:

1. **Порядок фаз в диспетчер-тике** (`FullDispatchTask.run()`):
   ```
   checkNewOrders → finishWithdrawals → assignNextDriveOrders → assignSequenceSuccessors
   → assignReservedOrders → assignFreeOrders     // сначала РЕАЛЬНЫЕ заказы
   → rechargeIdleVehicles                        // потом зарядка
   → prioritizedRepark → prioritizedParking → parkIdleVehicles  // парковка последней
   ```
   Робот, которому достался заказ, до фаз зарядки/парковки просто не доходит.

2. **Флаг `dispensable`** («заказ можно бросить»):
   - Recharge-заказ: `dispensable = !vehicle.isEnergyLevelCritical()` — заряжающегося МОЖНО снять с зарядки под заказ, если батарея не критическая.
   - Park-заказ: `dispensable = true` всегда.
   - Преемпция (`OrderAssigner.assignOrder`): если у выбранного робота уже есть dispensable-заказ, новый заказ НЕ назначается сразу — он кладётся в `OrderReservationPool` (резерв за этим роботом), текущий заказ абортируется (`abortOrder`, мягкий withdraw), и после перехода робота в IDLE фаза `assignReservedOrdersPhase` отдаёт ему зарезервированный заказ.

3. **Фильтр доступности** (`IsAvailableForAnyOrder`): робот в состоянии `CHARGING` считается доступным для заказов, **кроме** случая `needsMoreCharging`:
   ```java
   needsMoreCharging = state==CHARGING && !(keepRechargingUntilFullyCharged
       ? isEnergyLevelFullyRecharged() : isEnergyLevelSufficientlyRecharged())
   ```
   Плюс жёсткий гейт (`OrderAssigner.vehicleCanTakeOrder`): робот с критической батареей может взять ТОЛЬКО заказ, чья первая операция == его `rechargeOperation`.

### 1.2. Модель порогов — 4 значения на робота (не на систему!)

`Vehicle.EnergyLevelThresholdSet` (дефолты 30/90/30/90):
- `energyLevelCritical` (30): `level <= critical` → критично; только зарядочные заказы, recharge-заказ становится non-dispensable.
- `energyLevelGood` (90): `level <= good` → «degraded», робот — кандидат на отправку на зарядку.
- `energyLevelSufficientlyRecharged` (30): `level >=` → можно снимать с зарядки под работу (если `keepRechargingUntilFullyCharged=false`).
- `energyLevelFullyRecharged` (90): `level >=` → зарядка считается законченной всегда.

Гистерезис между good (вход на зарядку) и sufficiently/fully (выход) исключает дребезг.

### 1.3. Отбор роботов на зарядку (`IsIdleAndDegraded`)

Все условия сразу: интеграция `TO_BE_UTILIZED` ∧ ProcState IDLE дольше `rechargeIdleVehiclesDelay` мс ∧ State IDLE ∧ позиция известна ∧ нет order sequence ∧ `isEnergyLevelDegraded()` ∧ тип CHARGE в acceptable order types. Таймстамп ProcState — важная деталь: delay отсчитывается от момента перехода в IDLE, не от «сейчас».

### 1.4. Выбор зарядной станции (`DefaultRechargePositionSupplier.findRechargeSequence`)

Приоритетная цепочка: 1) property робота `tcs:assignedRechargeLocation` (жёстко: нет/занята → вообще не заряжаем); 2) `tcs:preferredRechargeLocation` (мягко); 3) **дешевейшая по стоимости маршрута** из всех локаций, разрешающих операцию зарядки. Краевые случаи:
- Станция исключается, если её точка доступа занята другим роботом **или уже является целью** другого робота (`TargetedPointsSupplier` — анти-double-booking);
- Проверка занятости расширяется на весь блок точки (у нас аналог — ячейки резервации);
- Стоимость до станции считается роутером от текущей позиции (у нас `map.distance`).
- Если станций нет — лог и молчаливый повтор на следующем тике (см. риск голодания в §8).

### 1.5. Парковка — три фазы + приоритеты

- Точка карты имеет флаг `isParkingPosition` и опциональный property `tcs:parkingPositionPriority` (int, меньше = важнее).
- `ParkIdleVehiclesPhase`: фильтр `IsParkable` = IDLE дольше `parkIdleVehiclesDelay` ∧ **текущая точка не парковочная** ∧ … → ближайшая свободная/не-целевая парковка (`DefaultParkingPositionSupplier`: assigned > preferred > nearest).
- `PrioritizedParkingPhase`: только парковки с приоритетом выше текущего, группировка по приоритету, внутри лучшей группы — ближайшая.
- `PrioritizedReparkPhase` (фильтр `IsReparkable`: робот УЖЕ на парковке) — перегоняет стоящих на низкоприоритетных парковках выше. Смысл приоритетов: высокоприоритетные парковки у зоны пиков — роботы «подтягиваются» к работе.

### 1.6. Конфиг-параметры (дефолты из `opentcs-kernel-defaults-baseline.properties`)

| Параметр | Дефолт |
|---|---|
| `rechargeIdleVehicles` | **false** (выключено из коробки!) |
| `rechargeIdleVehiclesDelay` | 0 мс |
| `keepRechargingUntilFullyCharged` | true |
| `parkIdleVehicles` | false |
| `parkIdleVehiclesDelay` | 0 мс |
| `considerParkingPositionPriorities` / `reparkVehiclesToHigherPriorityPositions` | false / false |
| `idleVehicleRedispatchingInterval` | 10000 мс |
| `vehiclePriorities` / `vehicleCandidatePriorities` | `IDLE_FIRST,BY_ENERGY_LEVEL` |

`PeriodicVehicleRedispatchingTask` (10 с) — вытаскивает дозарядившегося робота обратно в работу без внешнего события. `BY_ENERGY_LEVEL` — при прочих равных заказ получает более заряженный робот (пассивная балансировка износа).

### 1.7. Симуляция зарядки (loopback-адаптер)

`rechargePercentagePerSecond` (конфиг), тик 500 мс; при операции CHARGE: state→CHARGING, инкремент заряда до 100. Зарядка **абортируется** при любом из: пришла новая команда движения / state сменился / позиция изменилась → сразу `simulateNextCommand()`. Критичный комментарий из `canProcess()` (повторить у себя дословно): *нельзя требовать IDLE/CHARGING для принятия нового заказа — иначе робот, едущий на парковку/зарядку, обязан сперва доехать, и флаг dispensable теряет смысл.*

Риск порта: наш диспетчер — венгерский по матрице, а не пофазный перебор; фазовую модель кладём ВОКРУГ него (заказы→зарядка→парковка), внутри фаз — наш Hungarian.

## 4. VDA5050 / vda-5050-lib — что обязан уметь наш адаптер

Проверено по `vda-5050-lib@1.7.2` (MIT), уже в node_modules.

Протокол:
- `batteryState` в каждом state: `batteryCharge` (%, float, **обязателен**), `charging` (bool, **обязателен**), `batteryVoltage?`, `batteryHealth?`, `reach?` (м). AGV, умеющий только «хорошо/плохо», репортит 80/20 — пороги должны переваривать грубые значения.
- Действия `startCharging` / `stopCharging`: scope instant И node. Ошибка `batteryLowError` (FATAL) — стандартный сигнал «встал из-за батареи».

Поведение `VirtualAgvAdapter` (наш sim-робот), краевые случаи по `adapter/virtual-agv-adapter.js`:
1. **Пока `charging==true`, робот НЕ едет** (`_advanceTraverse` возвращается сразу) → **наш адаптер обязан сам слать `stopCharging`** (instant) и ждать `charging==false` в state перед отправкой заказа.
2. `startCharging` как instant отклоняется при активном заказе → правильная форма зарядной миссии: заказ до узла-зарядки с node-действием `startCharging` на последнем узле (как openTCS).
3. Заряд капится на 100%, но `charging` остаётся true до явного `stopCharging` — «зарядка закончилась» определяем сами по порогу.
4. Расход: линейный по дистанции, `batteryMaxReach` (дефолт 28800 м); зарядка: `100/3600/fullBatteryChargeTime` %/с (дефолт 1 ч); `lowBatteryChargeThreshold` (дефолт 1%): ниже — робот стоит, FATAL `batteryLowError`, снимается при заряде «порог+10%».
5. Для демо: `initialBatteryCharge`, `batteryMaxReach`, `fullBatteryChargeTime` задаются per-AGV при спавне — `packages/sim/src/fleet.ts` сейчас оставляет дефолты — поменять на демо-профиль (стартовый заряд 40–90%, укороченный reach), чтобы циклы зарядки были видны за минуты.

## 5. Open-RMF (rmf_task) — Вердикт: **идеи-только, 3 штуки; код не тянем**

Apache-2.0, C++/ROS.
- **Параметрическая тройка** (`Constraints.hpp`): `threshold_soc`, `recharge_soc` (дефолт 1.0), `drain_battery` (bool). Плюс per-robot `dedicated_charging_waypoint` («домашняя» зарядка; аналог openTCS `assignedRechargeLocation`).
- **Предиктивная вставка зарядки в план** (`ChargeBattery.cpp::estimate_finish`): планировщик считает SOC после каждой задачи и сам вставляет ChargeBattery-задачу; заказ, после которого робот не дотянет до зарядки выше `threshold_soc`, невыполним для этого робота. Формула: `t = 3600 * ΔSOC * capacity_Ah / charging_current_A`. Их грабли (задокументированы в коде): обязательно возвращать «зарядка не нужна», если робот уже у зарядки и заряжен — иначе планировщик зацикливается.
- **`finishing_request`** в конфиге флота: после последней задачи — `charge` / `park` / `nothing`.

Для v1 берём только реактивные пороги (openTCS-модель); предиктивный SOC-учёт в матрице диспетчера — этап 2 (будущий козырь против «просто порогов», требует откалиброванной модели расхода).

## 8. Риски и открытые вопросы

1. **Зарядок меньше, чем роботов**: openTCS при «все заняты» молчит и ретраит — критичный робот может голодать. Нужна своя очередь на станции + вытеснение: робот с `battery >= sufficient` на зарядке без заказа отгоняется на парковку, если станция нужна degraded/critical. openTCS этого НЕ делает — проектируем сами.
2. **Взаимодействие с yield-dispatch/PIBT**: заряжающийся робот — статичное препятствие; неправильный пин → либо сталкивают с зарядки, либо дедлок вокруг колонки зарядок (в дефолтной карте зарядки стеной x==0 — для демо возможно рассредоточить).
3. **Разношёрстность реальных AGV**: кто-то заряжается сам при контакте, кому-то обязателен stopCharging, кто-то репортит только 20/80%. Решение — per-model флаги `sendsStartCharging/needsExplicitStopCharging` (дыра №9); в адаптере заложить опциями сразу.
4. **Семантика выхода с зарядки**: дефолт «до полного» плох для загруженного склада; наш дефолт — «до sufficient» с конфигом.
5. **Открыто**: предиктивный SOC-учёт в Hungarian (этап 2); «домашние» зарядки vs общий пул (поддержать обе через assigned/preferred); `finishing_request` (charge/park/nothing) в v1?
