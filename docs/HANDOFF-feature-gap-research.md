## Список дыр (из честного сравнения с RDS, 11 авг)

1. **Зарядка**: политики, диспетчеризация на станции, парковка. (Приоритет 1 — без неё демо нечестное.)
2. **Зоны трафика**: односторонние проходы, запретные зоны, лимит роботов на зону.
3. **Редактор карт**: визуальный, импорт CAD/DXF; сейчас только программный grid + рестарт при смене карты.
4. **Периферия**: двери, лифты, конвейеры — Modbus TCP (`modbus-serial` npm — уже в утверждённом стеке).
5. **Мультиэтаж / группы карт.**
6. **Auth: роли, пользователи, аудит.**
7. **Статистика/отчёты** долгосрочные (kpi_snapshots уже пишутся — надо витрину).
8. **Свободная/гибридная навигация** (кривые, не-сеточные пути) — стратегический вопрос: нужна ли вообще для целевых складов (стеллажи = сетка)?
9. **Библиотека моделей роботов** (габариты, кинематика, калибровка).

## Ключевой вывод стратегической дискуссии 11 авг (сохранить в голове)

- Склады не платят за оркестратор — платят за проект «под ключ» (железо+интеграция+1C+поддержка). Софт = рычаг маржи и привязки, не SKU.
- UZ: труд дёшев, ROI слабый → покупатели = фарма, 3PL 2-3 смены, холдинги с бюджетом модернизации. РФ/КЗ: западные вендоры ушли, китайское железо без софта → рынок лицензий для интеграторов.
- Против RDS в лоб не позиционироваться («первый открытый web-оркестратор + 1C», не «замена RDS»).
- Три проверочных письма (LOI складу, gate поставщику, RU-интегратору) — быстрее любого анализа.
- Копирование донора сокращает софт-дыры с лет до месяцев, но полевую зрелость (реальное железо) не копирует никто.
